# アクセシビリティ改善計画

対象: TRPG GM App (`GM's Desk`) / 作成日: 2026-07-26
前提: 新規導入フェーズ・個人開発(1人)・日本国内の個人/趣味公開

---

## エグゼクティブサマリ

本アプリのアクセシビリティ成熟度は **L1(Ad hoc / 個人の善意依存)** と評価する。ただし L1 の典型例とは性質が異なり、「知識も意識も無い L1」ではなく **「良い実践が点在しているが、それを支える基盤が無い L1」** である。`prefers-reduced-motion` の全面尊重、Toast のライブリージョン、`role="progressbar"` / `aria-pressed` の適切な使用といった、中級者でも見落とす配慮が既に実装されている一方で、**ランドマーク・見出し階層・フォーカスリング・ラベル関連付けといった「土台」が丸ごと欠けている**。屋根から先に葺いた家に近い。

最大のリスクは 3 点に集約される。(1) `theme.js` の `inputStyle` が `outline: 'none'` を全入力欄に適用しており、キーボード利用者がフォーカス位置を完全に見失う。(2) 一覧の選択・タブ切り替え・タイプライタースキップが `<div onClick>` で実装されており(13箇所、`tabIndex` は 0 箇所)、キーボードから到達すらできない。(3) 補助テキスト色 `faint` のコントラスト比が **1.78:1**(要件 4.5:1)で、ヒント文が事実上読めない。

個人開発・趣味公開という規模を踏まえ、**12ヶ月で L3(Managed)相当**を目標とする。ただし「組織的ガバナンス」ではなく **「自動化とデザインシステムに規律を埋め込み、人間の注意力に依存しない状態」** を L3 の定義とする。1人で回す以上、チェックリストの遵守を意志力に頼る設計は必ず破綻するためである。

TRPG というドメイン特性上、この投資は単なる義務対応ではない。**卓上 TRPG は元来、音声と対話で成立する遊び**であり、視覚障害プレイヤーの参加実績が豊富なジャンルである。スクリーンリーダーで完走できる TRPG アプリは希少であり、ここは守りではなく明確な差別化余地にあたる。

### 1.2 強み(維持すべき資産)

これらは「あとから足すのが難しい」種類の実装であり、計画上の大きなアドバンテージである。

- **モーション制御が全面的に正しい** — `theme.js` の `motionAllowed()` を単一の判断点とし、ダイス演出・タイプライター・Toast アニメーションすべてが `prefers-reduced-motion` を尊重する。`matchMedia` 非対応環境でも静的表示に倒れる(WCAG 2.3.3 / 2.2.2 の一部を既に満たす)
- **Toast がライブリージョンとして正しく設計されている** — `role="status"` `aria-live="polite"` に加え、**items が空でもコンテナを描画し続ける**(コメントに意図が明記)。ライブリージョンの典型的失敗を回避済み
- **一部コンポーネントの ARIA が適切** — `AchievementProgressBar` の `role="progressbar"` + valuenow/min/max、`MoodChips` / `AchievementRow` の `aria-pressed`、装飾アイコンの `aria-hidden="true"`
- **`<html lang="ja">` が設定済み**(WCAG 3.1.1 適合)
- **設計意図をコメント・docs に残す文化が強い** — 34 本の plan/spec ドキュメントが存在。a11y 仕様を書き込む器が既にある
- **テスト総量が厚い** — 1326 ケース。`getByText` → `getByRole` への置換は「新規作成」ではなく「移行」で済む

### 1.4 目標レベル

**12ヶ月後の目標: L3 Managed(個人開発版の定義)**

「規程と組織的オーナーシップ」ではなく、以下を L3 の到達条件とする。

- a11y 要件が **デザインシステムの primitive 側に埋め込まれ**、画面実装者が意識しなくても既定で満たされる
- **CI が自動で違反を落とす**ため、忘却・多忙が品質に影響しない
- **完了定義(DoD)が文書化**され、将来の自分・AI エージェントが同じ判断を再現できる

## 4. 意思決定のための論点整理

個人・趣味公開のため法的強制力は低い。したがって「リスク回避」ではなく **「投資対効果」** で判断すべき案件である。

### なぜ今やるのか

#### 今やらない場合のコスト
- **修正コストの逓増** — 現在 8 画面・6,529 行。ランドマークとフォーカス設計は**土台の変更**であり、画面が増えるほど修正箇所が線形に増える。`docs/08-feature-ideas.md` に未実装案が控えている現状は、着手コストが最も低いタイミングを意味する
- **`<div onClick>` の増殖** — 既に 13 箇所。パターンが定着するほど、後発コードが同じ形を模倣する。デザインシステム側で正しい形を提供しない限り、この数は単調増加する
- **テスト資産の目減り** — 1326 ケースの 903 が `getByText`。マークアップを正しく直すほど**既存テストが壊れる**構造にある。先に構造を直すほど手戻りが小さい

#### 今やる場合の利得
- **ドメイン適合性が例外的に高い** — TRPG は元来、音声と対話で成立する遊びであり、視覚障害プレイヤーの参加実績が豊富なジャンルである。**スクリーンリーダーで完走できる TRPG アプリはほぼ存在しない**。ここは義務対応ではなく、明確な差別化余地
- **ソロ TRPG という形態との相乗** — 本アプリは GM を AI が務めるため、卓を囲む相手を必要としない。対面卓への参加障壁が高いプレイヤーにとって、そもそも本アプリの価値が最も高い。その層が使えない状態は、価値提案の中心が欠けていることを意味する
- **既存の強みを活かせる** — `prefers-reduced-motion` 対応・ライブリージョン設計・厚いテストが既にある。ゼロからの立ち上げではなく**穴埋め**であり、投入工数に対する到達点が高い
- **開発体験の副次的改善** — ESLint と CI は a11y 以外のバグも捕捉する。今回のビルド破壊(`main` が壊れたまま気付かれていなかった)は、CI があれば即座に検出できていた

### コスト比較

| 項目 | 今対応する場合 | 後で対応する場合 |
|------|----------------|------------------|
| 構造修正(ランドマーク/見出し) | 8 画面 × 30分 = 約4h | 画面数に比例して増加 |
| `<div onClick>` の是正 | 13 箇所、primitive 修正で大半が一括解決 | パターン増殖後は個別対応 |
| テスト移行 | 構造修正と同時に実施可能 | 二度手間(構造修正 → テスト修正) |
| CI 整備 | 3h、以降の退行を恒久的に防止 | 手動確認の継続コスト |
| **Phase 1+2 合計** | **約 33h** | — |

Phase 1(約 10h)だけでも Critical 3 件が解消され、キーボード利用者の「操作不能」状態は解消される。**費用対効果が最も高いのは Phase 1 と Phase 3(自動化)** であり、Phase 4 は余力に応じて調整してよい。

### 推奨アクション

1. **今週**: Phase 1 のうち `theme.js` 起因の 3 件(フォーカスリング・faint・line)を修正。単一ファイルの変更で全画面に効く
2. **1ヶ月以内**: `Card` / `Button` の primitive をキーボード対応にし、`<div onClick>` の増殖を止める
3. **6ヶ月以内**: ESLint + axe + CI を整備し、以降の品質維持を自動化に委ねる

## 5. ネクストステップ

### 直近の着手候補
1. `src/theme.js` の `inputStyle` から `outline: 'none'` を撤廃し、`:focus-visible` リングを定義する
2. `COLORS.faint` / `COLORS.line` をコントラスト基準を満たす値へ更新する
3. `src/components/ui/Button.jsx` に `type="button"` と `:focus-visible` を追加する
4. `src/components/ui/Card.jsx` の `onClick` 経路を `<button>` ベースに切り替える

### 確認が必要な事項
- **紙の質感という美意識との調整** — 本アプリの配色は「セピアの紙」という明確な意図を持つ。`faint` / `line` の darken は世界観に影響しうるため、コントラストを満たす範囲で最も明るい値を選ぶ、あるいは補助テキストのサイズ・用途を見直すなど、**意匠を壊さない解**を検討する必要がある(→ `design-critique` の結果と併せて判断)
- **対応スコープの優先順位** — 全画面一律か、プレイ体験の中核(Setup → Play)を優先するか。趣味公開であれば後者に絞る判断も合理的
- **スクリーンリーダー検証環境** — macOS の VoiceOver は利用可能。NVDA(Windows)まで見るかは費用対効果次第
